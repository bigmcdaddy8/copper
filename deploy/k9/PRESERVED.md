# K9 host scheduling — PRESERVED / PAUSED

**Status as of 2026-09-09 (phase 0W-AZ2B):** the K9 options-trading scheduled
jobs on the Azure VM `dragon` are **PAUSED** (all seven systemd timers
`disable --now`), ahead of a clean rebuild of `dragon` on Ubuntu 26.04.1 LTS
that repurposes the host as the primary **Dick's Laboratory futures collection**
host.

K9 is experimental and lower priority; it may be paused as needed. Its
definitions are **not lost** — see below.

## Why this file exists

The rebuild (0W-AZ2C) replaces the OS disk, so the *installed* copies under
`/etc/systemd/system/copper-k9-*` disappear. This note records the paused
state and the restoration path so K9 scheduling can be brought back
deliberately later.

## Original enabled state (pre-pause)

On `dragon`, all seven timers were `enabled` + `active (waiting)` from
2026-06-14 until 2026-09-09, when 0W-AZ2B ran
`systemctl disable --now copper-k9-*.timer` (the `timers.target.wants`
symlinks were removed; the unit files themselves remained on the old OS disk,
which is retained as rebuild rollback).

## ⚠️ `copper-k9-smart-shutdown` — do NOT re-enable on the futures host

`scripts/smart_shutdown.sh` uses the VM's managed identity to
`az vm deallocate` `dragon` at 10:15 CT Mon–Fri (unless a `pts/` session is
active). That belongs to the K9-era **~4.5 h/day, Mon–Fri, day-session-only**
lifecycle.

The futures-host model is **continuous Sunday pre-open → Friday post-close**,
with power controlled entirely from the Azure control plane (Automation
schedule), never by the guest. **`copper-k9-smart-shutdown` must stay disabled
(and its unit not installed) for as long as futures collection owns the host
lifecycle.** Re-enabling it would deallocate the VM mid-session.

(Observed 2026-09-09: even in the K9 era the 10:15 CT `smart_shutdown` run did
not reliably deallocate — the VM was still up ~1h40m later — further reason the
futures host must not depend on it.)

## Restoring K9 scheduling later (deliberate, not automatic)

Only if/when K9 is resumed **and** its shutdown behaviour has been reworked to
not fight the futures lifecycle:

```bash
# on the (rebuilt) host, as root:
install -m 0644 deploy/systemd/copper-k9-*.timer  /etc/systemd/system/
install -m 0644 deploy/systemd/copper-k9-job@.service /etc/systemd/system/
systemctl daemon-reload
# enable ONLY the jobs you actually want; do NOT enable smart-shutdown
systemctl enable --now \
  copper-k9-daily-close.timer copper-k9-weekly-flow-report.timer \
  copper-k9-compress-logs.timer copper-k9-tastytrade-entry-xsp.timer \
  copper-k9-morning-check.timer copper-k9-tastytrade-diagnostic.timer
```

The rebuilt host's fresh clone must be at
`/home/temckee8/Documents/REPOs/copper` (the units' hard-coded
`WorkingDirectory=`), and `.env` restored (mode 600), for the jobs to run.
